## 一、P1-b 剩余的三件事(全部在 BFF 侧,设计文档已定稿实现细节)

### 1. §4.1 服务令牌强制

模型管理路径(`providers*` / `models*`,**不含** `users/me/models`——身份绑定语义)在三个条件齐备时,强制改用服务账号 `ragAdminToken` 鉴权:

- 路径匹配(`MODEL_MANAGEMENT_PATH_RE`);
- feature flag 开启(见 §4.6);
- 后端配置了 `ragAdminToken`(缺失时自动退回成员令牌,不阻断)。

强制时跳过全部 `X-Intellect-*` 身份头注入(User/Role/Team/Project/Tenant)——服务令牌本身就是身份,混入成员身份头会让 RAG 归属判断混乱。实现上走 `rag-fetch.ts` 既有 `explicit` 分支(调用方显式 Authorization,不覆盖、不重试),**无需改动 `rag-fetch.ts`**。

### 2. §4.4 写权限门控(仅强制服务令牌时生效)

- 模型管理域的非 GET 写操作要求 `admin` / `owner` 角色(与 `llm-auth.ts`、`MemberRole` 既有口径一致);
- **fail-closed**:role 解析失败(TEAM 不可达、令牌无效)一律 403,不允许无法确权者以服务身份改租户配置;60s 角色缓存缓解 TEAM 抖动;
- flag 关闭时门控整体不生效,写请求由上游按成员令牌鉴权,与现状完全一致。

### 3. §4.6 feature flag

`BFF_MODEL_MGMT_SERVICE_TOKEN`,**默认关**。它是行为变更开关而非兼容开关:

- 关(默认)= 本批零行为变化,线上只有已合入的 P1-a"错误可见化"在起作用;
- 回滚 = 置 `false` 即可,无需回代码。

## 二、同源子问题:§4.5 默认模型的 PATCH 归类

flag 开启后 `PATCH /models/default`(设默认模型)命中"非 GET + 模型路径",要求管理员角色——**普通成员设默认模型会得到 403**。设计上认为默认模型是租户级共享配置、与实例管理同权限级别自洽,但需业务确认;若业务结论是"成员可设个人默认",则需将默认模型改为用户级数据,超出本次 BFF 门控的表达范围。flag 关闭期间无任何影响。

## 三、挂着的两个决策项(设计文档 §5 决策表)

| 项 | 内容 | 性质 | 影响 |
|---|---|---|---|
| **D1** | 生产 RAG 配置 `INTELLECT_TEAM_API_URL`(根治成员令牌 401) | 部署配置,需有生产权限者操作,不在 AgentUI 代码内 | 落地后 401 透传分支在生产自然不再触发;BFF 改动保留作为韧性 |
| **D2** | 服务令牌覆盖范围:**读+写**(模型配置视为租户级共享资源,设计**推荐**)还是仅读 | 业务决策 | 选"读+写"必须连带 §4.4 写门控一起开启;仅读则 §4.4 不生效。flag 生产开启等此项定论 |

§4.5 的默认模型 403 问题与 D2 同源,拍板 D2 时一并确认。

## 四、为什么开发不被阻塞

设计文档实施表明确:**"D2 有初步倾向即可开发,生产开启才等 D2 定论"**。flag 默认关,代码合入不改变任何现网行为;唯一真正卡进度的决定是"要不要现在写",不是 D2 本身;D1 只是部署配置,随时可补。

## 五、建议与验收口径

**建议**:P1-b(§4.1/§4.4/§4.6)现在即可按设计文档 §4 明细实施并补回归测试(flag 默认关合入);D1 找有生产权限的人配置;D2 拍板"读+写"后生产开 flag。

验收(设计文档 §验收表):flag 开 + ragAdminToken 配置正确时四个 GET 200、目录与默认模型下拉有数据;flag 开 + 非管理员非 GET 得 403;**flag 关 = 任何路径均不强制服务令牌、无角色门控(与现状一致)**;D1 落地后 flag 开/关行为一致(无 401)。
